# Online Patcher for Magisk

Универсальный однобинарный конфиг-управляемый патчер для Android, работающий
как Magisk-модуль. Не привязан ни к какому конкретному приложению или
устройству — что патчить и как, целиком описывается удалённым JSON-конфигом.
Держит один или несколько APK/файлов на устройстве пропатченными постоянно:

1. При загрузке (`post-fs-data`, ещё до сети) мгновенно восстанавливает все
   ранее применённые патчи из локального кэша — без сети, без риска
   стартовать с оригинальным (непропатченным) файлом.
2. Как только появляется сеть, встроенный демон (сам бинарник, без
   shell-лупа) начинает опрашивать конфиг на вашем сервере каждые N секунд
   (по умолчанию 10, настраивается сервером на лету).
3. Конфиг описывает **список целей** (`targets`) — APK и/или обычные файлы,
   каждая со своим набором правил `pattern → replace`. Для каждой
   изменившейся цели: APK — извлекает ZIP, применяет правила, пересобирает
   и подписывает (v1 JAR-подпись, ключ AOSP platform test-key); обычный
   файл — просто копия + замена. Bind-mount поверх оригинала, перезапуск
   приложения (`am force-stop`), если это APK со своим package_name.
4. Если конфиг не менялся — не трогает файлы вообще (ни чтения, ни хэширования).
5. Уберите цель из списка `targets` на сервере — при следующем опросе патчер
   сам вернёт оригинал (revert) для неё. Либо выполните возврат вручную в
   любой момент: `patcher revert`.
6. О начале/успехе/неудаче патчинга и о revert'е может сигнализировать
   RGB LED-кольцо устройства, если оно есть (см. "LED-уведомления" ниже) —
   опционально, не часть основной логики.

## Структура репозитория

```
├── src/                       исходники C-патчера
│   ├── patcher.c              точка входа и вся логика (см. ниже)
│   ├── http_fetch.h           HTTPS GET через dlopen'нутый системный libssl/libcrypto
│   ├── rules_json.h           узкий JSON-парсер конфига (мульти-таргет + метаданные)
│   ├── cache_index.h          персистентный реестр кэша (по одной строке на цель)
│   ├── patcher_state.h        персистентное состояние демона (url/интервал/exec-хэш/...)
│   ├── sha1.h                 SHA1 (для кэш-ключа и подписи)
│   ├── bignum.h                bignum modexp для RSA-подписи (pure C)
│   ├── signing_identity.h     embedded ключ/сертификат (AOSP platform test-key)
│   ├── puff.c / puff.h        DEFLATE-декодер (эталонный код zlib, public domain)
│   ├── genkey_aosp.go         генератор signing_identity.h из platform.pk8/x509.pem
│   ├── platform.pk8           приватный ключ AOSP platform test-key (DER)
│   └── platform.x509.pem      сертификат к нему
├── module/                    шаблон Magisk-модуля (без бинарника — его кладёт build)
│   ├── module.prop
│   ├── post-fs-data.sh        `patcher boot` — одна строка, всё остальное в бинарнике
│   ├── service.sh             `patcher daemon &` — тоже одна строка
│   ├── customize.sh           чинит exec-биты после Windows-упаковки zip
│   └── sepolicy.rule
├── config.example.json        пример конфига для хостинга на сервере
├── config_url.txt             URL вашего конфига — build кладёт его в модуль как config_url
├── build.ps1 / build.cmd      сборка бинарника + сборка Magisk-модуля + zip
└── out/                       результат сборки (создаётся build-скриптом, не в git)
```

## Установка на устройство

1. **Пропишите адрес своего конфига до сборки:** впишите URL одной строкой в
   файл [`config_url.txt`](config_url.txt) в корне репозитория. Build-скрипт
   положит его в модуль под именем `config_url` рядом с бинарником (см. "Как
   задать адрес сервера" ниже). Оставите файл пустым — модуль соберётся, но
   патчер ничего не будет делать, пока файл `config_url` не появится.
2. Соберите `out\online_patcher.zip` (см. "Сборка" ниже) и установите через
   Magisk (Modules → Install from storage).
3. Выложите свой конфиг (см. формат ниже, пример — `config.example.json`) на сервере.
4. Перезагрузите устройство.

Логи — `<module_dir>/patcher.log` (там же, где бинарник, — `<moddir>/bin/patcher`).

## Как задать адрес сервера

В код никакой URL не зашит. На старте патчер ищет адрес конфига по цепочке:

1. сохранённое состояние `state.conf` — если сервер ранее перенаправил опросы
   через поле `config_url` в самом JSON, адрес оттуда переживает перезагрузки;
2. файл `config_url` рядом с модулем — `/data/adb/modules/online_patcher/config_url`,
   одна строка с URL;
3. если ни там, ни там нет — патчер просто ничего не делает и пишет в лог
   `no config_url ... will do nothing`.

Для **самого первого** запроса взять адрес неоткуда, кроме файла `config_url`,
поэтому один раз его нужно задать. Три способа:

- **До сборки (рекомендуется):** впишите URL одной строкой в
  [`config_url.txt`](config_url.txt) в корне репозитория. При сборке
  build-скрипт кладёт его содержимое в модуль как файл `config_url` (рядом с
  бинарником). Пустой файл — модуль без адреса, зададите вручную позже.
- **На уже установленном модуле — вручную:**
  ```bash
  adb shell su -c "echo 'https://ваш-сервер/config.json' > /data/adb/modules/online_patcher/config_url"
  ```
  (затем перезагрузка либо перезапуск демона).
- **Через сам конфиг:** как только сервер хоть раз отдал JSON с полем
  `config_url`, адрес сохраняется в `state.conf` и файл `config_url` больше не
  нужен — удобно для миграции на другой/резервный адрес.

## Как это работает

### Откуда патчер узнаёт, что и куда патчить

Никаких хардкодов: все пути (кэш, состояние, лог, временная директория)
патчер вычисляет **от расположения собственного исполняемого файла**
(через `/proc/self/exe`), а какую цель и как патчить — исключительно из
удалённого JSON-конфига. URL этого конфига читается один раз из файла
`config_url` рядом с бинарником; дальше сервер может сам перенаправить
будущие опросы на другой адрес через поле `config_url` в самом JSON
(сохраняется в состоянии, переживает перезагрузки).

### Формат конфига

Хостится на вашем сервере, отдаётся по HTTPS. При каждом запросе патчер
передаёт query-параметры устройства и прошивки (какие есть — не у всех
устройств/прошивок присутствуют все свойства, отсутствующие просто не
отправляются): `serial`, `manufacturer`, `model`, `device`, `platform`,
`fingerprint` (полный build fingerprint прошивки), `android` (версия),
`sdk` (API level), `build_id`. Так сервер может отдавать разные правила
разным устройствам/платформам/прошивкам, ничего не зная о конкретном
устройстве заранее.

```json
{
  "poll_interval": 10,
  "config_url": "https://example.com/config.json",
  "exec": "",
  "targets": [
    {
      "apk_path": "/system/priv-app/some-app/some-app.apk",
      "package_name": "com.example.someapp",
      "rules": [
        { "file_name": "assets/config.cfg", "pattern": "https://old.example.com", "replace": "https://new.example.com" }
      ]
    },
    {
      "file_path": "/vendor/etc/selinux/vendor_mac_permissions.xml",
      "rules": [
        { "pattern": "</policy>", "replace": "<signer signature=\"...\">...</signer></policy>" }
      ]
    }
  ]
}
```

Полный пример конфига с обоими типами целей (APK и SELinux-политика) — в [`config.example.json`](config.example.json).

- **`targets`** — массив независимых целей. Можно патчить сколько угодно
  разных APK/файлов одним конфигом одновременно. Какой ключ используете —
  тот и определяет, как цель обрабатывается, никакого отдельного поля
  `type` не нужно:
  - **`apk_path`** — цель это APK: извлечь ZIP, применить правила, пересобрать,
    переподписать (v1 JAR), bind-mount.
  - **`file_path`** — цель это обычный плоский файл (конфиг, XML-политика и
    т.п.): просто копия + substring-замены + bind-mount, без ZIP и без
    подписи. `rules[].file_name` для таких целей указывать не нужно —
    подставляется автоматически (сопоставлять маской не с чем, файл один).
  - `package_name` — только для `apk_path`-целей: чтобы найти и подмонтировать
    все копии APK в `/data/app/<package>-*/base.apk` (не только основной
    путь), и чтобы было что перезапустить (`am force-stop`) после патча. Для
    `file_path`-целей не нужен и игнорируется.
  - `rules[].file_name` — поддерживает glob-маску (`fnmatch`, например
    `assets/*.cfg`); для `apk_path`-целей обязателен (внутри ZIP нужно
    знать, к какому файлу применять правило), для `file_path`-целей не нужен.
  - `rules[].pattern` / `replace` — обычная подстрока (не regex). Для
    бинарных данных (например, байты с `\0` внутри, которые JSON-строкой не
    передать) — `pattern_hex` / `replace_hex` (чётное количество hex-цифр,
    декодируется в сырые байты). `replace` дополнительно можно задать через
    `replace_file` — путь к файлу на устройстве, чьё содержимое читается в
    момент применения правила (для больших/бинарных замен, которые неудобно
    инлайнить в JSON целиком). Любая комбинация валидна: `pattern`+`replace`,
    `pattern`+`replace_hex`, `pattern`+`replace_file`, `pattern_hex`+`replace`,
    `pattern_hex`+`replace_hex`, `pattern_hex`+`replace_file`. Если задано
    несколько вариантов для одного поля — приоритет: `pattern_hex` над
    `pattern`; `replace_file` над `replace_hex` над `replace`.
  - **Уберите цель из массива `targets`** на сервере — при следующем опросе
    патчер автоматически отмонтирует её и вернёт оригинал. Это основной,
    "конфиг как источник истины", механизм отката.
  - Кэш каждой цели зависит **только от содержимого этой цели** (путь +
    package_name + правила), а не от всего файла конфига — правка одной цели
    (или `poll_interval`/`config_url`/`exec` наверху) не заставляет остальные
    цели пересобираться заново.
- `poll_interval` — сколько секунд ждать между опросами. Меняется на лету —
  следующий цикл уже использует новое значение, сохраняется между перезагрузками.
- `config_url` — сервер может перенаправить будущие опросы на другой адрес
  (миграция/резервный URL); тоже сохраняется и переживает ребут.
- `exec` — shell-команда, которая выполняется **от root** (`/system/bin/sh -c`)
  ровно один раз при каждом изменении её текста (хэш сравнивается с последней
  выполненной — при неизменном тексте не запускается повторно каждые 10 сек).
- Сеть недоступна, HTTP-статус не 2xx, пустое тело или невалидный JSON — во
  всех случаях патчер просто пропускает цикл ("nothing to do"), никогда не
  подставляет какой-то дефолтный патч сам от себя.

### Ручной откат (revert)

Кроме автоматического отката через удаление цели из конфига, есть прямая
команда — не требует сети, работает мгновенно:

```bash
su -c "/data/adb/modules/online_patcher/bin/patcher revert"
```

Отмонтирует все цели из локального реестра кэша, перезапускает
соответствующие приложения и полностью очищает реестр. После этого патчер,
если продолжает работать в фоне (`daemon`), при следующем успешном опросе
конфига применит патчи заново — если хотите отключить его насовсем,
остановите/удалите Magisk-модуль или процесс `patcher`.

### Кэш и офлайн-восстановление после ребута

- **`cache.tsv`** — персистентный реестр, **по одной строке на каждую
  пропатченную цель**: `путь : package_name : sha1(оригинал) :
  sha1(пропатченный) : sha1(конфиг) : путь_к_пропатченному_файлу`.
- **`post-fs-data.sh`** (режим `boot`) — при каждой загрузке, ещё до сети,
  быстро (доли секунды) проходит по ВСЕМ строкам реестра: совпадает ли
  текущий оригинал каждой цели на диске с `orig`-хэшем? Если да — сразу
  монтирует. Никакой сети, никакой распаковки APK на этом шаге.
- **`service.sh`** запускает демон (режим `daemon`) — тот же бинарник, но
  с полным циклом: сеть, пересборка/откат при необходимости, `exec`.

### Как патчер решает, нужно ли что-то делать (и не трогает файлы зря)

1. **Fingerprint по размеру файла.** `content_fingerprint()` — для файлов
   **меньше 8 МБ** (конфиги, XML-политики) берётся честный полный SHA1
   (дёшево — файл маленький, точность важнее). Для файлов **от 8 МБ**
   (APK) — размер файла плюс 128 КБ каждые 16 МБ (плюс хвост): для APK на
   350 МБ это ~3 МБ чтения вместо 350 МБ.
2. **Fingerprint вообще не считается, если конфиг не поменялся.** Текст
   свежепойманного конфига сравнивается (по SHA1, дёшево) с текстом последнего
   успешно обработанного. Совпадает → выходим из цикла немедленно, ни разу не
   притронувшись ни к одной цели.

### LED-уведомления (опционально, под конкретное железо)

На устройстве, для которого этот патчер изначально разрабатывался
(Яндекс Станция, кастомный лаунчер), обычные Android-уведомления
(`cmd notification post`) не отображаются — у лаунчера нет системной шторки.
Вместо этого патчер напрямую пишет в sysfs RGB LED-кольца устройства
(`/sys/class/leds/chiron:{red,green,blue}:ring0-47/brightness`, без каких-либо
разрешений Android):

- **жёлтый ↔ синий**, по кругу, по 1 сек на цвет — идёт реальная пересборка
  цели (мигает в фоновом процессе весь **срок сборки**, не привязано к
  таймауту)
- **зелёный, сплошной, 10 сек** — пересборка и монтирование прошли успешно
- **красный, сплошной, 10 сек** — ошибка на любом из шагов пересборки
- **синий** (3 короткие вспышки) — откат (revert) цели

Пути в `led_set()` (`patcher.c`) жёстко привязаны к конкретному устройству —
на другом железе либо поменяйте их на актуальные, либо просто уберите вызовы
`led_*`/`notify_*`, эта часть не влияет на основную логику патчинга.

### Однопроцессность

Полный цикл (extract → sign → repack) пишет в файл для конкретной цели
(имя выводится из хэша пути к ней — `patched_<hash12>.apk`, так что
несколько целей не конфликтуют друг с другом), но `post-fs-data` и демон всё
равно блокируются друг от друга файловым локом (`patcher.lock`, `flock`) —
параллельный запуск второй копии просто логирует и выходит.

### Подпись APK

APK подписывается v1 (JAR) подписью приватным ключом (`src/platform.pk8` /
`platform.x509.pem`, по умолчанию — AOSP platform test-key). Если целевое
устройство собрано этим же ключом (типичный dev-keys образ) — переподписанное
системное приложение не теряет signature-защищённые разрешения. Вся PKCS7/DER-
структура подписи и RSA-2048 modexp реализованы в чистом C — внешние
`jarsigner`/`apksigner`/`zip` не используются.

Если понадобится другой подписывающий ключ — `src/genkey_aosp.go` генерирует
`signing_identity.h` из пары `<key>.pk8` + `<key>.x509.pem`.

## Сборка

Требуется Android NDK (тестировалось на r27c). Скрипт сам ищет NDK в стандартных
местах, либо путь можно указать явно.

```powershell
.\build.ps1                      # собрать + упаковать zip
.\build.ps1 -NdkPath D:\ndk\...   # если NDK не находится автоматически
.\build.ps1 -SkipZip              # собрать только папку модуля, без zip
```

или то же самое из cmd.exe / двойным кликом: `build.cmd`.

Результат:
- `out\online_patcher\` — готовая папка модуля (бинарник + скрипты + `module.prop`)
- `out\online_patcher.zip` — готов к установке через Magisk Manager

## Запуск без Magisk (ramdisk/init.rc)

Бинарник полностью самодостаточен и не содержит зашитых путей/URL — все
пути выводятся из его собственного расположения на диске, поэтому его можно
вызвать без единого аргумента:

```bash
patcher boot     # быстрый офлайн-монтаж из кэша, для ранней стадии загрузки
patcher daemon   # полный цикл, никогда не возвращается (свой sleep-луп)
patcher revert   # снять все патчи и восстановить оригиналы
patcher          # без аргументов = daemon
```

`module/post-fs-data.sh` и `module/service.sh` — тонкие однострочные
обёртки (нужны только потому, что Magisk хукает именно `.sh`-файлы) — если
кладёте бинарник прямо в init.rc-сервис на ramdisk, эти скрипты не нужны
вовсе, просто вызывайте `patcher boot`/`patcher daemon &` напрямую
соответствующими строчками `service`. Не забудьте положить файл `config_url`
рядом с бинарником в любом случае (см. "Как задать адрес сервера" выше) — при
запуске без Magisk `customize.sh` не выполняется, так что автоматической
записи адреса не будет, создайте файл сами.

Позиционные аргументы (`<work_dir> <log_file> <cache_index_file>
<patched_apk_out> [mode]`) по-прежнему поддерживаются, если нужно
переопределить пути для локального тестирования.

## Известные ограничения

- JSON-парсер (`rules_json.h`) — намеренно узкий под конкретную схему
  (`targets[].{apk_path|file_path, package_name, rules[]}` + несколько ключей
  верхнего уровня). Не general-purpose парсер.
- HTTPS-клиент не проверяет сертификат сервера (годится для собственного
  контролируемого сервера; для публичного/недоверенного сервера это нужно
  включить в `http_fetch.h`).
- `exec` выполняется без песочницы, от root — конфиг-сервер полностью доверенный.
- Патчинг переупаковывает файл целиком, а не патчит "на месте" — `replace`
  любой длины относительно `pattern` работает без проблем с ZIP-офсетами.
- `file_path`-цели умеют патчить **любой** файл, включая системные
  SELinux-политики (`vendor_mac_permissions.xml` и т.п.) — мощно, но и
  рискованно: эффект от изменения такого файла применяется только после
  **перезагрузки** (PackageManagerService читает его при сканировании
  пакетов на загрузке, не на лету), и повреждённый/невалидный XML там может
  сказаться на SELinux-метках *других* приложений, не только вашей цели.
  Проверяйте валидность результата (`</policy>` ровно один, XML парсится)
  до того, как полагаться на такой патч через реальный ребут.
